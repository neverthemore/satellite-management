# Postman-коллекция для Satellite Management System

Файлы в этом комплекте:

| Файл | Назначение |
|---|---|
| `openapi.yaml` / `openapi.json` | OpenAPI 3.0.3-спецификация сервиса, собранная по аннотациям `@Operation`/`@Tag` из контроллеров и по DTO/JPA-классам проекта (springdoc-openapi в самом проекте уже подключён в `build.gradle.kts`, эта спецификация соответствует тому, что он сгенерирует на `/v3/api-docs`) |
| `Satellite-Management-System.postman_collection.json` | Коллекция запросов (25 шт., 4 папки) с тестовыми скриптами |
| `Satellite-Local.postman_environment.json` | Окружение с переменными для локального запуска (`localhost:8080`) |
| `build_collection.py` | Скрипт, которым сгенерирована коллекция (для воспроизводимости/доработки) |

---

## 1. Импорт в Postman

1. Скачать и установить Postman: https://www.postman.com/downloads/
2. `File → Import` → перетащить оба `.json`-файла (коллекцию и окружение) **или** импортировать `openapi.yaml` напрямую (Postman умеет генерировать коллекцию из OpenAPI-спеки автоматически — это альтернативный способ получить тот же результат).
3. В правом верхнем углу выбрать окружение **Satellite Local (localhost:8080)**.

## 2. Запуск сервиса перед тестированием

Сервису нужны Postgres, Kafka и gRPC-сервис телеметрии (`satellite-telemetry` на порту 9091) — см. `application.yaml`. Минимальный вариант поднять зависимости:

```bash
# Postgres
docker run -d --name satellite-db -p 5432:5432 \
  -e POSTGRES_DB=satellite_db -e POSTGRES_USER=satellite_user -e POSTGRES_PASSWORD=satellite_pass \
  postgres:16

# Kafka (пример с redpanda, легче поднимается для локальной разработки)
docker run -d --name satellite-kafka -p 9094:9094 redpandadata/redpanda start --smp 1 --overprovisioned \
  --kafka-addr PLAINTEXT://0.0.0.0:9094 --advertise-kafka-addr PLAINTEXT://localhost:9094
```

gRPC-клиент телеметрии подключается лениво, поэтому если `satellite-telemetry` не поднят — REST API всё равно будет работать (просто `internalTemperature`/`externalTemperature` останутся `null`, что как раз проверяется тестом `NO_DATA` в папке Telemetry).

Запуск самого сервиса:
```bash
./gradlew bootRun
# или через Docker:
docker build -t satellite-spring .
docker run -p 8080:8080 --network host satellite-spring
```

Проверка, что поднялось: `http://localhost:8080/swagger-ui.html` и `http://localhost:8080/v3/api-docs`.

## 3. Порядок прогона коллекции

Запросы **специально упорядочены сверху вниз** внутри каждой папки так, чтобы более поздние запросы использовали результат более ранних (chaining через `pm.collectionVariables`):

1. **Constellations CRUD** — сначала создаём группировку `Test-Constellation` (переменная `constellationName`), затем читаем список, читаем по имени, проверяем 404 на несуществующей, и только в конце — удаление (с проверкой повторного 404).
   ⚠️ Если запускать не всю коллекцию Runner'ом, а отдельные запросы вручную — не удаляйте группировку до того, как пройдёте папки 2–4, иначе они получат 404/422 вместо ожидаемых успешных ответов.
2. **Space Operation Center** — добавляет спутники `COMM-SAT-1` и `IMG-SAT-1` в ту же группировку, затем миссии/деплой/сводки, в конце деактивирует `COMM-SAT-1`.
3. **Satellites CRUD** — читает добавленные спутники (первый запрос сам подставляет `satelliteId` в переменную коллекции для следующих).
4. **Telemetry** — читает телеметрию тех же спутников (без запущенного `satellite-telemetry` ожидаемо получите `NO_DATA`, это штатно и тоже проверяется тестом).

Прогнать всё разом: кнопка **Runner** → выбрать коллекцию и окружение → Run. В отчёте Runner'а будет видно каждый `pm.test(...)` с результатом pass/fail.

## 4. Что проверяют скрипты (папка Tests каждого запроса)

- Позитивные сценарии: код ответа (200/201/204), соответствие структуры JSON схемам из `openapi.yaml`, согласованность связанных полей (например `activeSatellites <= totalSatellites`, `totalConstellations == Object.keys(constellations).length`).
- Негативные сценарии: 404 на несуществующих ресурсах, 422 с телом `{error, message, timestamp}` при бизнес-ошибках (`GlobalExceptionHandler`), некорректный `type` у `SatelliteParam`.
- Глобальный тест уровня коллекции (виден в `Collection → Tests`): нет 5xx-ошибок и время ответа < 3с — применяется ко всем 25 запросам автоматически.

## 5. План скринкаста (для п.2 задания)

Рекомендуемая последовательность показа (5–8 минут):

1. Коротко показать `openapi.yaml`/Swagger UI — откуда взялась спецификация.
2. Показать импорт коллекции + environment в Postman.
3. Развернуть дерево коллекции — показать 4 папки и объяснить логику разбиения по контроллерам.
4. Открыть один GET-запрос — показать вкладку `Tests`, объяснить один-два `pm.test`.
5. Открыть один POST-запрос с телом (`Добавить спутники в группировку`) — показать `Body → raw JSON`, отправить, показать ответ и прошедшие тесты.
6. Показать негативный кейс (`404` или `422`) — отправить, показать, что тест на код ошибки зелёный.
7. Запустить весь сценарий через **Collection Runner** — показать итоговый отчёт (25/25 или сколько прошло, объяснить, если что-то упало из-за отсутствия Kafka/gRPC-заглушек).
8. Резюме: что покрыто, что можно расширить (авторизация, negative-тесты на валидацию батареи вне диапазона [0,1] и т.д.).

Записать можно любым инструментом экрана (OBS Studio, встроенная запись Windows/macOS, Loom и т.п.) — программа записи не входит в этот комплект, я лишь готовлю материал для демонстрации.
